# 付録　証拠から報告までを一つの例でたどる

[目次](README.md) · [失敗パターン](08-failure-patterns.md)

このアキュムレータは教材用に設計した合成例であり、歴史的プログラムではありません。`SPEC-ACC-v1` を権威ある契約とします。表の値は契約からの手計算であり、実行記録の捏造ではありません。バイナリ、実際の run ID、検査済み実装は存在しないので、最後も実候補の CONFORMED ではなく演習上の判断です。

## 1. 問いと証拠

二バイトの要求を受け取るアキュムレータを再実装するとします。契約の状態は 0..255 の整数 value です。`01 n` は飽和加算、`02 00` はリセットです。それ以外の `02 n` は `invalid_operand`、他の opcode は `unknown_operation` を返します。長さが 2 でなければ opcode の検査前に `invalid_length` を返します。エラー時は状態不変、成功時は `ok` です。要求ごとに処理後の value と結果コードを観測します。

`E-CONTRACT` はこの人工契約であり、権威は本例の中だけです。実際の考古なら、出典の版や入力・道具のハッシュを追加します。望ましい動作を原版の規則として書いてはいけません。

## 2. 仮説と判別

`C-SAT` は「加算が 255 を超えたら 255 にする」です。契約を見る前なら、飽和、回り込み、拒否が候補です。`E-CONTRACT` を得た後は「教材契約がそう定義している」という範囲で `CONFIRMED` にできます。一標本から全域の経験則に昇格したのではありません。

10 に 1 を足すと三候補とも 11 にでき、判別力がありません。250 に 10 を足せば、255、4、エラーで 250 のままと予測が分かれ、誤実装を見つけられます。

## 3. READY に必要な条件

形式、操作、エラー優先順、観測境界は契約で定義されています。画面、永続化、タイミング、並行処理は最初から本例の要求にないため対象外です。既存要求を避けるための除外ではありません。通常加算、上限、リセット、不正入力、エラー後の正常要求を必須例とします。

これで READY 審査を説明できますが、実プロジェクトには審査記録と実装許可も必要です。比較は value と結果コードの厳密一致です。許容差、ソート、フィールド省略はありません。

## 4. 先に参照列を計算する

ケース A は独立に 10 から開始します。ケース B は独立に 250 から開始し、B01〜B08 を順に処理します。各行は要求処理後の観測です。入力 bytes は十六進数、状態値は十進数です。

| 時点 | 入力 bytes | 処理前 value | 参照 value | 結果コード |
|---|---|---:|---:|---|
| A01 | `01 01` | 10 | 11 | `ok` |
| B01 | `01 0A` | 250 | 255 | `ok` |
| B02 | `01 00` | 255 | 255 | `ok` |
| B03 | `02 00` | 255 | 0 | `ok` |
| B04 | `01 FF` | 0 | 255 | `ok` |
| B05 | `02 01` | 255 | 255 | `invalid_operand` |
| B06 | `03 00` | 255 | 255 | `unknown_operation` |
| B07 | `01` | 255 | 255 | `invalid_length` |
| B08 | `02 00` | 255 | 0 | `ok` |

B08 はエラー後の回復を検査し、B03 では代用できません。九時点で二必須フィールドずつ、合計十八のフィールド比較です。欠測を一致に数えません。この集合は宣言した標本であって、全入力の網羅的証明ではありません。

## 5. 失敗する候補を入れる

`CAND-WRAP` は `(value + n) mod 256` を使い、それ以外は契約どおりと仮定します。紙上の候補であって、実行成果物ではありません。A01 は通りますが、B01 は参照 255 に対して 4 です。最初の差は次のとおりです。

```text
仕様：SPEC-ACC-v1
候補：CAND-WRAP（教材上の仮定）
時点：B01
入力：01 0A
フィールド：value
参照：255
候補：4
結果コード：両方 ok
結論：value が不一致。成功コードは内容比較の代用にならない。
```

B03 では両方リセットされゼロになるので、そこだけを見れば以前の誤りが消えます。最初の差で実行を止めるなら、B02〜B08 は未実行かつ未完了と報告し、省略しません。

## 6. 修正と欠測

式を `min(255, value + n)` に修正し、十分広い整数で加算してから上限を適用します。先に八ビットへ変換すれば、まだ回り込みます。この推論は人工契約から直接支えられます。

次に、B05 の記録には value だけあり、結果コードがないとします。255 だけでは、不正要求を拒否したのか、成功扱いで何もしなかったのか分かりません。合格でなく欠測と報告します。新たに実行して必須フィールドを取得するまで比較は未完了です。

## 7. 書いてよい報告

紙上では次のように書けます。

> SPEC-ACC-v1 に基づく計算で、CAND-WRAP は B01 の value が参照と異なる。修正式はこの反例を解消する。九つの参照時点と十八の必須フィールドを定めた。実候補、実行記録、観測成果物はなく、CONFORMED の裁定はしていない。

実際に実行するときは、候補識別、基準と観測器の版、入力と成果物のハッシュ、実取得数、差分、停止理由、審査を追加します。必須条件をすべて満たしてから「この候補は SPEC-ACC-v1 の宣言事例に適合」と言えます。それでも歴史的ソフトウェアとの互換性ではありません。

## 8. 自己確認と答え

1. A01 で回り込みを除外できるか。できません。両式が同じなので B01 を使います。
2. B05 は value だけ正しければ合格か。いいえ。結果コードも必須です。
3. B03 の一致は B01 の差を取り消すか。いいえ。各時点が必要です。
4. 九例一致で全状態を証明できるか。できません。宣言した例を支えるだけで、全域の主張には別の推論や検査が必要です。
5. 本文は成功した実行報告か。いいえ。実際の run がない、計算可能な教材です。
6. どの不明点が妨げになるか。必須結果コードの欠測です。要求されていない表示タイミングは妨げませんが、確認済みにもなりません。

### 出典と主張の範囲

歴史的入力はありません。`E-CONTRACT` は人工契約で、数値はその計算結果です。観測と解釈の分離、欠測の保持、最初の差の扱いは [S3、O2、P3](../../inventory.md#固定來源索引)の教訓に対応しますが、それらの動作をこの例へ移したのではありません。
