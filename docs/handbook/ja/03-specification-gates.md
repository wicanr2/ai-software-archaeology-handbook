# 03　仕様は実装前の証拠審査

[前の章](02-hypotheses.md) · [目次](README.md) · [次の章](04-oracles.md)

仕様は、考えを正式な文章にするだけのものではありません。実装者と審査者が、合法な入力、状態の変化、比較可能な出力、欠落の扱い、受入条件について同じ答えを持てる必要があります。答えがない箇所は明記し、実装者の推測に任せません。

## 三つの状態

| 状態 | 何がそろっているか | 許される作業 |
|---|---|---|
| `DRAFT` | 確認済みの断片を含むこともあるが、必要条件が不足した契約 | 調査、隔離実験、捨てられる試作 |
| `READY` | 範囲と動作に証拠があり、不明点、事例、受入条件を審査済み | その範囲の正式実装 |
| `CONFORMED` | 特定の候補版が宣言した比較と必須検査を通過 | 同じ範囲で適合結果を引用 |

これは工程の状態であり、主張の確信度ではありません。READY で不明な機能を除外できるのは、依頼された切片を妨げない場合だけです。仕様を縮めて必須機能を完了扱いにしてはいけません。CONFORMED も除外項目を証明しません。

## READY の審査項目

実装可能な仕様には最低限、次が必要です。

1. サブシステム、対象版、仕様版、実際の利用者目標。
2. 個々の主張と出典。原版証拠、推論、意図的差異、新規設計を区別。
3. 入力、出力、初期状態、不変条件。
4. エラー、未対応版、必須データ不足時の動作。
5. 観測フィールドと取得境界。
6. 判定基準、正常例と反例、比較規則。
7. 既知の不明点、阻害するかとその理由、明確な対象外範囲。
8. 受入条件、審査者と判断、変更後の再検証条件。

反例がない仕様は、もっともらしい出力しか検査しない危険があります。誤った候補を落とせる例を少なくとも一つ用意し、テストがその違いを観測できるようにします。

## 小さな契約の形

以下は付録の人工的な教材契約であり、原版から復元した形式ではありません。

```text
仕様：SPEC-ACC-v1
状態：整数 value、一つだけ。範囲は 0..255。
入力：要求ごとに正確に二 bytes。opcode、operand。
01 n：value = min(255, value + n)、ok を返す。
02 00：value = 0、ok を返す。
02 n（n が非ゼロ）：invalid_operand、状態不変。
その他の opcode：unknown_operation、状態不変。
長さが 2 以外：invalid_length、状態不変。opcode より先に検査。
観測：各要求の処理後の value と結果コード。
対象外：永続化、画面、タイミング、並行処理、他の版。
必須例：通常加算、上限、リセット、不正入力、エラー後の正常操作。
```

「自分たちが定義した契約」と「原版がそう動く」は違います。人工契約は合成テストの権威ある参照になれますが、歴史的互換性の証明にはなりません。実際の考古では、各規則を証拠につなぐか、不足を明示します。

## 実装中に不足を見つけたら

原版は不正要求に対して状態を変えてからエラーを返すらしいのに、仕様は原子的な失敗を要求しているとします。証拠を確かめて、該当条項と事例に戻ります。旧版の合格報告を残し、そのラベルを新版へ流用しません。

審査とはコード一行ごとに利用者へ質問することではありません。事実は技術者が調べます。動作、形式、構成、忠実度、公開方法を実質的に変える取捨選択は利用者が決めます。許可された差異だと仕様に記し、後で不具合や原版事実と混同しないようにします。

### 出典と主張の範囲

[P2、T2、T3](../../inventory.md#固定來源索引)はゲートと異なる状態の仕様の共存を記録しています。確認した版では Talos の制御契約は READY、実行証跡の保存形式は DRAFT であることが `CONFIRMED` です。審査表は `STRONG_INFERENCE`、三状態ゲートは既存の規則でもあります。
