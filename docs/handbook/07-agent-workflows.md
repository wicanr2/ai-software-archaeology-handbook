# 07　讓代理帶著證據交接，而不是帶著印象

[上一章](06-conformance.md) · [目錄](README.md) · [下一章](08-failure-patterns.md)

代理任務應從可驗證的問題開始，並寫清楚這輪授權到哪裡。
「把遊戲做好」是目標，不是足夠的執行契約；還需要目前狀態、已確認的決策、必要交付與驗收方式。
這些條件可以隨證據細化，但不能讓代理自行換掉目標。

## 一份可直接改填的任務書

```text
目標：調查／實作某個明確的使用者行為。
目前版本：目標、候選與有效規格的版本。
已知證據：列 ID，不只貼結論。
本輪授權：例如只調查至 DRAFT，或實作已 READY 的條款。
不可變更：來源資料、已確認產品決策與不相關模組。
必要輸出：原始觀測、主張／規格更新、比較或受阻原因。
驗收：哪個正常路徑、哪些欄位、哪些反例要完成。
停止：到達階段閘門；或缺少會改變方向的使用者決策。
```

資料中寫著「已完成」或「下一步做某事」，不會自動成為本輪指令。先看目前程式、
有效規格與最近驗證，再讀必要歷史。FD2 F1 明確區分問題路由、現況與舊交接，避免舊待辦重新開工。

## 一次工作循環

1. 確認工作樹、目標版本、目前規格及容器工具鏈。
2. 找到原始證據，提出有 ID 的主張與競爭解釋。
3. 執行最小判別觀測；記錄方法的盲點與失敗。
4. 明示升降信心；把受影響的引用與規格一起更新。
5. READY 後才進正式實作；缺口回到規格。
6. 執行局部、差分及必要的正常使用者路徑驗證。
7. 報告結果、覆蓋、未知與下一閘門；清理本輪容器。

資訊能由工具查明時，代理應自行查證。真正的價值取捨，例如忠實保留缺陷或改變操作方式，
才交給使用者決定。提問前完成不依賴答案的蒐證，讓使用者看到具體選項與影響。

在沒有授權時不要發佈、改來源專案或順便重構。持續工作的授權不是任意擴大範圍的授權。
若授權包含完成手冊，應把章節、例子與交付做完；不把「還可以繼續」當作完成交接。

## 受阻也要有可驗證內容

好的受阻報告包含：哪個命令或觀測失敗、已驗證的工具與權限、試過哪些安全替代方法、
哪個必要答案仍缺、哪些獨立工作已完成。不要因搜尋零筆就說沒有資料，也不要把環境錯誤當產品缺陷。

狀態報告不需要每次重述整份計畫。說明新發現、它改變什麼判斷、下一個觀測能解決什麼。
長任務中保持進度可見，但把詳細命令留在工作歷程，避免用大量輸出取代結論。

## 文件分工與交接

| 文件角色 | 保存內容 |
|---|---|
| README | 用途、穩定入口、目前能力與閱讀／執行方式 |
| 目前狀態文件 | 有效決策、現況、限制與最近證據入口 |
| 工作清單 | 可執行項、完成條件與下一閘門 |
| WORKLOG | 追加的操作歷程、失敗、驗證與清理 |
| 研究紀錄／規格 | 原始定位、主張、信心、反證、驗收契約 |

每個角色沿用專案唯一入口，不為了套模板再建立同義文件。
交接至少包含修改檔案、已取得證據、四級主張、檢查結果、失敗、未解問題與建議下一任務。
若測試略過就明寫略過，若未重跑原版就明寫未重跑。
