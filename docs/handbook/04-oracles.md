# 04　行為基準也有能力邊界

[上一章](03-specification-gates.md) · [目錄](README.md) · [下一章](05-differential-testing.md)

行為基準（oracle）是用來裁決某個問題的參考。它可以是原版程式、外部模擬器、
明確規格或獨立參考實作；重要的是能說明它為什麼有資格裁決這個欄位。
「用了另一套工具」不是完整理由，另一套工具也可能共用同一個錯誤假設。

## 依問題選基準

| 問題 | 合適的參考形態 | 應保留的限制 |
|---|---|---|
| 原版菜單如何回應按鍵 | 固定版本原版，從正常入口重播 | 模擬環境、初始狀態、按鍵接受時點 |
| 格式解碼是否得到相同內容 | 獨立解碼器與相同輸入 | 支援版本、編碼、錯誤處理及共用程式來源 |
| 指令狀態轉移是否相同 | 已知起始狀態的原版／外部核心 | 僅覆蓋被比較的暫存器、記憶體與指令 |
| 硬體參數的合理近似 | 公開硬體契約 | 規格近似，不能稱為實機逐週期相同 |
| 合成教學例子的正確結果 | 明確人工契約與獨立手算 | 只證明例子內的契約，沒有歷史相容性意義 |

手冊、攻略與使用者記憶也能指出值得調查的行為，但要分清描述、觀察與程式實際狀態。
同一個「戰場大小」可能指畫面視野或內部陣列；先確認名詞指的層次，再判斷衝突。

## 一次可回查的執行

固定原版／候選身分、基準版本、工具 image ID、設定、起始存檔或狀態、輸入序列與停止條件。
設定明確的執行預算，不讓失敗後的背景程序繼續跑。保存原始觀測，再產生比較；
不能用正規化後的資料覆寫原始輸出。

觀測邊界應是可辨識事件，例如「處理完第 17 個請求」「剛到下一條指令入口」或
「指定畫格完成繪製」。只說「送按鍵後等一秒」不能保證每次都到同一狀態。
有些原版只能採時間驅動，這時記錄不確定性、重播次數與對齊條件，不捏造決定性。

Parhelion 的 Capture 會在 dispatch 邊界擷取，並處理取指令已前進的差異；
這樣的狀態差分適合核心驗證，不能代替遊戲從正常選單走到目標的證據（P3）。

## 先驗重播，再驗候選

同一個基準、同一條路線跑兩次，先比較基準彼此的結果。如果它自己不一致，
先判斷亂數、排程、設定、擷取時機或非決定性欄位，不把所有差異算在候選頭上。
兩次一致只支持這次重播條件，不是所有條件都決定性的證明。

OnePCE 的紀錄指出，Mesen2 全速模式可能略過繪製，狀態到指定幀但畫面仍舊；
擷取腳本因此固定關閉跳幀（O1、O3）。這說明「模擬已完成」與「觀測已更新」需要分開驗證。

檢查觀測器要有正對照與錯誤路徑：工具不存在應報錯，必要附件缺失應阻止驗收，
空目錄不能變成零差異。要觀察圖片內容時，用合成圖片確認尺寸、列距、通道及裁切沒有被轉換器破壞。

## 基準衝突怎麼處理

先對齊版本與定義，再逐欄比較各基準的證據力。Talos 的 TAS 規格明列外部語料的時序限制，
使用另一來源支持局部訂正，同時保留其他欄位的驗收（T4）。不要把「外部」等同「不會錯」。

訂正基準時保存原值、修正值、理由、支持證據、受影響案例與未解範圍。
若沒有足夠證據裁決，標 `UNKNOWN` 並阻止相關符合性宣告。不能選最容易讓候選通過的那個參考。

PCM／DAC／PIT 等時序問題依本專案停止線優先使用公開契約，記為
`hardware-spec approximation`；需要重新開啟硬體考古，必須有另外的明確授權。

### 來源與主張範圍

[O1、O3、T4、P3、W2](../inventory.md#固定來源索引)分別提供擷取、語料勘誤、狀態邊界與格式參考的例子。
來源內容為 `CONFIRMED` 的文件／程式碼觀察；選基準與重播流程是 `STRONG_INFERENCE`。
沒有把上述模擬器的結果等同原始硬體實測。
