# 附錄　從證據到符合性報告：一個完整演練

[目錄](README.md) · [回到失敗模式](08-failure-patterns.md)

這個累加器是本書人工設計的合成教學例子，不來自任何原版程式。
`SPEC-ACC-v1` 是本例的權威契約；下表是依契約手算的結果，不是捏造的執行紀錄。
沒有二進位檔、真實 run ID 或實作測試，所以最後只產生教學裁決，不冒稱實際候選已 CONFORMED。

## 1. 題目與證據

假設你要重寫一個接受兩位元組請求的累加器。教學契約定義狀態 value 是 0..255 的整數。
`01 n` 做飽和加法，`02 00` 重設；其他 `02 n` 回 `invalid_operand`，
其他 opcode 回 `unknown_operation`。請求長度不是 2 時先回 `invalid_length`。
錯誤不改狀態；成功回 `ok`。每次請求後觀測 value 與結果碼。

證據 `E-CONTRACT` 就是上段明定的人工契約；它只對此例有權威。
若這是真實考古，你需要另外記錄來源版本、輸入與工具雜湊，不能把自己想要的行為寫成原版規則。

## 2. 假說與判別

主張 `C-SAT`：加法超過 255 時取 255。讀到契約前可把飽和、回繞、拒絕列為候選；
取得 `E-CONTRACT` 後，`C-SAT` 可標 `CONFIRMED`，範圍僅為「教學契約如此定義」。
這不是只靠一筆樣本提升全域信心。

初值 10 加 1 的三種候選都可能得到 11，沒有判別力。
初值 250 加 10 則分別得到 255、4 或錯誤且保留 250，因此可揭露錯誤實作。

## 3. READY 所需條件

`SPEC-ACC-v1` 的格式、操作、錯誤順序及觀測邊界已由契約定義。
排除畫面、持久儲存、時序與併行；這些排除僅因本例根本沒要求它們，不是躲避原有需求。
必要案例包括一般加法、上限、重設、非法輸入及錯誤後的下一次合法請求。

本例可據此示範 READY 審查；真實專案仍需留下審查紀錄與合法的實作授權。
比較規則為 value 與結果碼完全相同，無容差、無排序、無欄位省略。

## 4. 先把參考序列算出來

案例 A 獨立起始於 10；案例 B 獨立起始於 250，B01–B08 依序執行。
每行都在該請求處理完後取樣。十六進位只用於請求 bytes，狀態數值是十進位。

| 檢查點 | 輸入 bytes | 操作前 value | 參考 value | 結果碼 |
|---|---|---:|---:|---|
| A01 | `01 01` | 10 | 11 | `ok` |
| B01 | `01 0A` | 250 | 255 | `ok` |
| B02 | `01 00` | 255 | 255 | `ok` |
| B03 | `02 00` | 255 | 0 | `ok` |
| B04 | `01 FF` | 0 | 255 | `ok` |
| B05 | `02 01` | 255 | 255 | `invalid_operand` |
| B06 | `03 00` | 255 | 255 | `unknown_operation` |
| B07 | `01` | 255 | 255 | `invalid_length` |
| B08 | `02 00` | 255 | 0 | `ok` |

案例 B08 驗錯誤之後還能正常處理，不能由 B03 代替。
九個檢查點、每點兩個必需欄位，共十八個欄位比較；不能把未取得的欄位計為相符。
這組案例是宣告範圍的抽樣，不是所有可能輸入的窮舉證明。

## 5. 放進一個會失敗的候選

錯誤候選 `CAND-WRAP` 用 `(value + n) mod 256`，其餘行為假設依契約。
這是紙上定義的候選，不是實際執行產物。A01 會通過，B01 的 value 卻是 4，參考為 255。
第一個分歧如下：

```text
規格：SPEC-ACC-v1
候選：CAND-WRAP（教學假定）
檢查點：B01
輸入：01 0A
欄位：value
參考：255
候選：4
結果碼：兩者均為 ok
結論：value 不相符；不能以成功結果碼代替內容比較。
```

如果只看 B03 重設後的值，兩邊又同為 0，差異會被洗掉。
若依第一分歧停止後續執行，未執行的 B02–B08 要記未完成，不能從報告省略。

## 6. 修正與缺失觀測

修正候選為 `min(255, value + n)`，先在足夠寬的整數中相加，再限制上限；
若先轉成八位元再取最小值，仍會回繞。這個推導由人工契約直接支持。

另外設想觀測檔在 B05 只留下 value，沒有結果碼。即使 value 是 255，
仍不知道候選是拒絕非法請求，還是成功卻沒動作。此時只能報告缺失觀測，不能算 B05 通過。
重新執行並取得缺欄位之前，必要比較未完成。

## 7. 可寫與不可寫的報告

紙上可寫：

> 依 SPEC-ACC-v1 手算，CAND-WRAP 在 B01 的 value 與參考不符。
> 修正公式可消除這個反例；九個參考檢查點及十八個必要欄位已列出。
> 尚無實際候選、執行紀錄與觀測附件，未作 CONFORMED 裁決。

若未來真的執行，需補候選身分、基準／觀測器版本、輸入及產物雜湊、
實際收集數、差分結果、停止原因與審查紀錄。全部必要條件滿足後，
才可聲明「該候選對 SPEC-ACC-v1 的宣告案例符合」；仍不能稱為某款歷史軟體的相容實作。

## 8. 自我檢核與答案

1. A01 通過能排除回繞嗎？不能，兩公式在此相同；要看 B01。
2. B05 只有數值正確算通過嗎？不能，結果碼也是必要欄位。
3. B03 兩邊都為零會取消 B01 的差異嗎？不會，規格要求每個檢查點。
4. 九個案例全相符能證明所有狀態嗎？不能，只支持宣告案例；全域證明另需推導或更完整方法。
5. 能把本文當成成功執行報告嗎？不能，這是可手算的教學資料，沒有實際 run。
6. 哪種未知阻塞本例？必要結果碼缺失會阻塞；未要求的畫面時序不阻塞，也不因此被證實。
