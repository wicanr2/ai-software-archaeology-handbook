# 01　讓證據能被另一個人重新找到

[上一章](00-principles.md) · [目錄](README.md) · [下一章](02-hypotheses.md)

證據首先是可定位的觀測，不是替觀測取的名字。「記憶體某位置在扣血後減少」與
「這個欄位是生命值」是兩個層次。前者需要輸入、位置與擷取方法，後者還需要排除其他解釋。

一張截圖也不是完整證據。它至少要能回答：哪個程式版本、哪個起始狀態、送了什麼輸入、
在哪個時間邊界擷取、是否經過縮放或轉色。缺少其中幾項仍可留下作線索，但不能假裝可精確重播。

## 最小證據卡

這是人工工作表，不是正式 schema。沒有取得的資料寫 `UNKNOWN`，不要填假的範例雜湊。

| 欄位 | 要記什麼 |
|---|---|
| 證據 ID 與問題 | 穩定識別碼；這筆觀測要裁決什麼 |
| 輸入身分 | 原檔名、SHA-256、版本；對文件另記儲存庫與完整提交 |
| 原始定位 | 檔案路徑／頁碼／符號；地址另寫工具與位址空間 |
| 環境與方法 | 工具版本、容器 image ID、設定、命令、輸入序列、預算 |
| 起始及取樣條件 | 存檔、亂數狀態、事件或畫格邊界、擷取前後狀態 |
| 原始產物 | 路徑、雜湊、大小；畫面再記尺寸與像素格式 |
| 原始觀察 | 實際看到的值；不要先套語意名稱 |
| 主張與等級 | 解釋、支持與反對證據、信心、缺失項 |

來源文件的 SHA-256 證明你讀的是哪份筆記，不能取代筆記所引用的 EXE 雜湊。
Git 提交固定來源版本，工作樹可能在閱讀期間前進；取證與驗證都應讀同一個固定版本。

## 保留原始定位，附加語意

反組譯時保留原始函式名、原始運算元、位元組及位址。自訂名稱容易看成既定事實，
應以附加註解或受版控的索引記錄「語意、信心、來源」，並在匯出時自動合併顯示。
只把索引藏在另一個檔案，要求接手者記得查，不能算完整的證據傳遞。

對同一筆定位，呈現方式應像下面的工作表，而不是只剩 `health` 這個名稱：

| 原始定位 | 附加解釋 | 信心 | 證據 |
|---|---|---|---|
| 原檔＋原始運算元＋明示的位址空間 | 可能參與某次狀態更新 | `HYPOTHESIS`，尚未證實 | 指向取樣與讀寫端；缺失另列 |

IDA 線性位址、段內位移與檔案偏移不應並列成同一種數值。跨工具對照要保留各自基準與映射理由。
函式與資料流的關係以分析資料庫為主；平面組合語言文字適合搜尋，不足以證明所有間接存取。

## 搜尋不到之前，先證明搜尋看得到

春之石的掃描曾因只接受 `int` 助憶碼而漏掉工具顯示成 `wait` 的呼叫（S2）。
所以「零命中」至少要通過四個檢查：

1. 正對照：工具能找到一個已知存在的目標嗎？
2. 範圍：讀到的是全部相關區段，還是工具已判成程式碼的子集？
3. 表示法：是否兼顧符號、直接運算元、折入基底的偏移及間接存取？
4. 分母：掃了多少項、略過多少項、多少項無法解析？

有大量讀取卻找不到寫入時，繼續追查取址與間接寫入。直接交叉參照缺項不能證明沒有寫入。
先分類為「這個搜尋方法未找到」，保留 `UNKNOWN`，不要改寫成「程式不存在此行為」。

## 觀測工具也需要正對照

用已知尺寸與色彩的合成圖驗證截圖轉換；用已知事件驗證 trace；檢查工具是否真的啟動、
完成及寫出結果。WinCV 的截圖轉換錯誤曾污染後續字型推論（W1）。
修好工具後，回查所有依賴其輸出的結論，不能只修下一次擷取。

在共用主機上，分析與擷取放進有資源限制、外層逾時及明確生命週期的 Docker 容器；
原始資料唯讀，寫入目錄先驗 UID/GID，完成後清理本次容器。
本書只保存必要的來源索引與原創摘要；不因案例可存取就匯入其原版素材。
