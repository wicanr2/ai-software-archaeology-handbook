03　規格是實作前的證據審查

上一章 · 目錄 · 下一章

規格不只是把想法寫得正式。它必須讓實作者與審查者對同一件事有共同答案： 什麼輸入合法、狀態如何改變、哪些輸出可比較、缺失怎麼處理，以及做到哪裡才算符合。 無法回答的部分要明列，不留給實作者補猜。

三個狀態

狀態 已具備什麼 可以做什麼
DRAFT 調查中的契約，可能包含已證實片段，但仍缺必要條件 蒐證、隔離實驗、可丟棄原型
READY 範圍與行為有證據；未知、案例及驗收條件已審查 在該範圍內寫正式實作
CONFORMED 指定候選版本通過規格宣告的比較與必要檢查 在同一範圍內引用符合性結果

這是工程狀態，不能代替主張的四級信心。READY 可以排除某個未知功能， 前提是它不阻塞使用者要求的切片；不能藉由縮小規格，把原本需要的功能算成完成。 CONFORMED 也不使排除項自動得到證明。

READY 審查表

一份可實作的規格至少包含：

  1. 子系統、目標版本、規格版本與實際使用者目標。
  2. 逐項主張及來源，區分原版證據、推論、刻意差異與新增設計。
  3. 輸入、輸出、起始狀態與不變量。
  4. 錯誤、未支援版本及缺少必要資料時的行為。
  5. 可觀測欄位與取樣邊界。
  6. 行為基準、正常及反例案例、比較規則。
  7. 已知未知、阻塞與不阻塞理由、明確排除範圍。
  8. 驗收條件、審查者與結論；改版時的重驗條件。

沒有反例案例的規格特別容易只驗到「看起來合理」的輸出。至少放入一個會使錯誤候選失敗的案例， 並保證測試能觀察那個差異。

一個小規格的形狀

下列是附錄人工定義的教學契約，不是從原版逆向出的資料格式：

規格：SPEC-ACC-v1
狀態範圍：單一 value，整數 0..255。
輸入：每個請求恰好兩個 bytes：opcode、operand。
01 n：value = min(255, value + n)，回覆 ok。
02 00：value = 0，回覆 ok。
02 n（n 非 0）：invalid_operand，狀態不變。
其他 opcode：unknown_operation，狀態不變。
長度非 2：invalid_length，狀態不變；先於 opcode 檢查。
觀測：每個請求處理完後的 value 與結果碼。
排除：持久儲存、畫面、時序、併行與其他版本。
必要案例：一般加法、上限、重設、錯誤輸入及錯誤後繼續操作。

「這是我們定義的契約」與「原版就是如此」完全不同。前者可以成為合成測試的權威參考， 但不能拿來證明歷史相容性。真正考古時，要把每一條公式接到來源或明示未完成。

實作途中遇到缺口

假設實作者發現原版對長度錯誤的請求可能先改狀態再報錯，而目前規格要求原子失敗。 先確認證據，再退回受影響的條款與案例；保留已通過的舊版本報告，不把舊標籤直接套在新版本。

審查不是每一行程式都請使用者決定。可由證據查明的事由工程師查明； 真正改變玩法、格式、架構、原版忠實度或公開方式的取捨，才由使用者作決定。 規格中應明寫這種差異是授權設計，避免未來把它當作缺陷或原版事實。
