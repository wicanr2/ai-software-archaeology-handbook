# 以證據驅動的軟體考古：方法草案

狀態：`DRAFT`。本文件是第 0 階段的研究整理，尚未經階段審查，
不是已驗證的工具架構、資料格式或正式手冊章節。
先完成繁體中文內容，待中文版完成並審查後，再擴充英文與日文。

## 要解決的問題

測試通過，表示程式滿足那組測試的條件；原版相容性則需要在宣告範圍內，
對同一輸入與狀態比較原版或指定基準。兩者之間不能省略觀測與比較。
MM2 的最終顯示層未經過離屏測試，春之石的單調測試不能區分生命值與經驗值，
都是來源可查的反例（[F01、F04](failure-patterns.md)）。

本專案既有核心流程如下。箭頭表示產物之間的依賴，不表示只走一次；
遇到矛盾，回到受影響的證據、假說或規格。

```text
證據 → 假說 → 規格 → 行為基準 → 實作 → 差分驗證 → 符合性
```

「行為基準（oracle）」必須具體到來源、版本、輸入、觀測邊界與能裁決的欄位。
它可以是原版程式、外部模擬器、權威規格或獨立參考實作，但不能把來源相異
的結果統稱為同一種原版證明。WinCV 的壓縮格式與介面、OnePCE 的畫面、Talos
的語料與 Hatari，分別需要不同契約（W2、O1、T4；完整出處見[來源索引](inventory.md#固定來源索引)）。

## 每階段的契約

下表是依本專案 AGENTS／PLAN 要求與 R1–R7 整理的規範建議。
案例觀察可回查；表中的工程提煉屬 `STRONG_INFERENCE`。
機器可讀產物僅列未來所需概念，尚未決定或建立 schema。

| 階段 | 輸入 | 輸出／機器可讀產物候選 | 信心要求 | 離開條件 | 典型失敗 |
|---|---|---|---|---|---|
| 證據 | 明確問題、合法輸入、工具與目標版本 | 證據 ID、來源定位、雜湊、原始觀測、擷取條件 | 直接觀察與解釋分開；缺項標 UNKNOWN | 他人能定位同份輸入、理解觀測方法與限制 | 缺工具版本；觀測器出錯；把零命中當不存在 |
| 假說 | 可追溯證據與相互矛盾之處 | 主張、競爭解釋、支持／反對證據、反證方法 | 起始 HYPOTHESIS；升降級都記原因 | 已有能分開候選的檢驗，或明確保留阻塞未知 | 合理命名冒充事實；兩個假說都會過的測試 |
| 規格 | 有範圍的主張、已知差異與未知 | 輸入／輸出、狀態、不變量、驗收案例、排除範圍 | DRAFT 不授權正式實作；READY 要有證據契約 | READY 所需欄位與阻塞判斷齊全，完成證據審查 | 默默填預設值；把自訂行為寫成原版 |
| 行為基準 | READY 契約、固定版本、起始狀態與輸入 | 執行 ID、觀測集合、工具與輸入雜湊、停止原因 | 能裁決哪些欄位須明示；不可比者保留 UNKNOWN | 已取得所需觀測，重播條件與基準限制可核查 | 舊畫面、跳幀、缺檔被略過、語料自身有錯 |
| 實作 | READY 規格與已建立的比較條件 | 窄範圍候選實作、規格關聯、局部驗證 | 不以實作方便提升假說；缺口回規格 | 規格內輸出可被觀測，能送進比較 | 自行接受自己的輸出；未審查原型進主線 |
| 差分驗證 | 原始參考觀測、候選觀測、預先宣告的比較規則 | 首個分歧、期望／實際、覆蓋分母、缺失、容差 | 只斷言已比較的欄位與案例 | 完成宣告案例並解釋差異；未完成不可當相符 | 調整期望掩蓋錯誤；只看最後畫面；裁掉差異卻不報 |
| 符合性 | 規格、執行紀錄、比較報告及未覆蓋項 | 有版本的符合性報告、範圍、限制與證據鏈 | CONFORMED 只屬於宣告契約；不等於全面相容 | 所有必要條件通過，缺失與例外均按規格處理 | 把 smoke、skip 或局部無分歧當全系統完成 |

規格階段要先定義需要的基準案例；行為基準階段使其可執行並取得資料。
允許在 DRAFT 期間做隔離實驗以取得證據，不能把表格誤讀成「未 READY 不能觀察原版」。

## 兩條互不取代的狀態軸

主張信心固定用 `CONFIRMED`、`STRONG_INFERENCE`、`HYPOTHESIS`、`UNKNOWN`。
它回答「這一句話有什麼證據」。規格則用 `DRAFT`、`READY`、`CONFORMED`，
回答「這個有範圍的契約走到哪個工程階段」。

一份規格可以明列非阻塞的 `UNKNOWN`；通過已聲明範圍的比較，不會讓未知欄位
跟著變成已證實。反之，一份 DRAFT 可以包含已核對的原始位元組，仍因輸出或
驗收案例不足而不能進正式實作。Talos T2／T3 與 Parhelion P2 支持逐契約分開處理。

來源使用其他信心詞彙時保留原文，再解釋其證據。春之石 S3 的「證據充分」
仍缺結算端，不能只因讀起來肯定就映射成 `CONFIRMED`。

## 先把比較題目說清楚

一次比較至少要回答：

1. 比的是哪個輸入版本、哪個子系統與哪條使用者路徑？
2. 原版與候選各自從什麼狀態開始，在哪個事件邊界取樣？
3. 基準能裁決哪些欄位？有什麼已知缺陷？
4. 哪些值要精確相同，哪些允許轉換或容差？依據是什麼？
5. 必要資料缺失、測試略過、未實作或提早停止時，結果如何表達？
6. 符合性聲明的分母、排除範圍與重跑方法是什麼？

OnePCE O1 的色彩對應、參考視窗與最後一列排除，必須跟「零差異」一起讀；
Parhelion P3 同時有 `Diverge` 與 `Err`，沒有分歧仍可能是未實作指令造成停止。
不能只取一個看起來成功的欄位。

## 證據衝突時的處理

先確認目標版本、起始狀態、觀測範圍與工具是否相同，再判斷是否真正衝突。
若是真矛盾，保留原始資料與舊主張，標示新證據及受影響的引用；回到原規格
修正後，再沿同一條驗證路徑重跑。不能刪掉失敗原因，也不能讓被撤回的解釋
繼續出現在現行格式文件而沒有提示。MM2 M1／M2 是後一種風險的現成案例。

針對錯誤工具輸出，先修復與驗證觀測鏈，再重查依賴它的判斷。WinCV W1 的
字型推論曾在轉換器修好後仍未回頭重驗，顯示「工具修好」與「知識訂正」是兩件工作。

## 實作及驗證的停止線

先建立最小且完整的垂直鏈，讓輸入、資料、規則、輸出與比較連得起來。
遊戲產品的完成仍須正常玩家入口；指令核心從原版擷取狀態的差分實驗只能證明
該核心切片。跨平台與替代流程各有自己的覆蓋，不以一個平台樣本外推全部。

遇到 PCM／DAC／PIT 等硬體時序，依本專案共用規範優先使用公開硬體契約，
標明規格近似（`hardware-spec approximation`），不因剩餘時鐘差異開啟無限逆向。
Talos 的歷史案例僅用來說明基準邊界，不是授權本手冊重新鑽研其硬體實作。

第 0 階段的停止線則是有來源的盤點與方法草案送審。本輪已達送審材料條件，
仍等待專案負責人審查，不把自查當成第 1 階段授權。

## 對 PLAN 的審查建議

以下尚未改動既有階段或資料格式：

- `STRONG_INFERENCE`：第 1 階段應把「驗證觀測工具」與「基準的裁決範圍」納入證據及 oracle 章節。依據 F05–F07。
- `STRONG_INFERENCE`：第 2 階段模型應明示測試略過、必要觀測缺失及提早停止，避免與 mismatch／match 混用。依據 O2、P3。
- `HYPOTHESIS`：在跨語言版本中沿用來源 ID 與主張關聯，可降低翻譯造成的信心漂移；待中文版穩定後驗證。
- `UNKNOWN`：第 4 階段應選哪個真實介接案例。Talos 尚未完成整機，OnePCE 涉及 ROM 與畫面資料，Parhelion 有較窄的狀態比較；本輪不代替使用者定案。

本草案沒有選定 JSON／JSONL 載體、schema、介接器或工具架構，也未建立 CLI。
